# 부록 B. 확인 문제 풀이

## 1장

1. ① user-service 가 post-service 의 주소와 API 를 알아야 해서, 듣는 서비스가 늘 때마다 user-service 를 고쳐야 한다. ② post-service 가 꺼져 있으면 부르기가 실패해 닉네임 바꾸기가 실패하거나 소식이 사라진다. (③ 대답을 기다리므로 post-service 가 느리면 함께 느려진다)
2. 지우지 않는다. 보관 기간 동안 남겨 두고, 컨슈머 그룹마다 읽은 위치만 기억한다. 그래서 꺼졌던 컨슈머가 이어서 읽거나, 다른 그룹이 같은 소식을 처음부터 따로 읽을 수 있다.
3. 같은 키의 소식은 같은 파티션에 들어가 보낸 순서대로 읽힌다. 한 회원이 닉네임을 빠르게 여러 번 바꿔도 순서가 뒤바뀌지 않아, 마지막 닉네임이 최종 값이 된다.
4. "지금 당장은 두 DB 가 다를 수 있지만, 잠시 뒤에는 결국 같아진다" 는 뜻이다. 작성자 이름은 1초 늦어도 괜찮지만, 계좌 이체처럼 잠깐이라도 어긋나면 안 되는 일(돈이 사라지거나 두 번 생김)에는 곤란하다.

## 2장

1. Kafka 4 는 스스로 클러스터 정보를 관리하는 KRaft 방식만 쓰기 때문이다.
2. Kafka 는 기본으로 토픽 자동 생성이 켜져 있어서, 서비스가 처음 그 토픽을 쓰거나 들으려 할 때 저절로 만든다.
3. `PUT /api/auth/me` 는 이미 있는 `/api/auth/**` 라우팅 규칙으로 user-service 에 가고, `AuthFilter` 의 규칙상 로그인이 필요한 주소로 검사되기 때문이다.

## 3장

1. 토큰 안에는 옛 닉네임이 남아 있으므로, 앞으로 쓰는 글이 게이트웨이를 거쳐 옛 닉네임으로 저장된다.
2. 소식은 나갔는데 DB 저장이 실패하면, post-service 는 바뀌지도 않은 닉네임으로 writer 를 고친다. 없었던 일을 알린 셈이 되어 두 DB 가 어긋난다.
3. 이벤트는 "이미 일어난 사실" 을 알리는 것이기 때문이다. `CHANGE_NICKNAME` 은 "바꿔라" 는 명령처럼 읽힌다.
4. Kafka 가 꺼져 있을 때 기본값 60초 동안 닉네임 바꾸기 요청이 멈춰 버리기 때문이다. 3초만 기다리고 포기하게 했다.

## 4장

1. 그룹이 처음 붙은 뒤에 온 소식만 읽으므로, 3장에서 미리 보낸 소식은 읽지 않고 지나간다(writer 가 고쳐지지 않는다).
2. 클래스를 함께 쓰면 한쪽이 바꿀 때 다른 쪽도 함께 다시 배포해야 해서, 서비스를 따로 배포하려던 목적이 깨진다. 약속은 JSON 모양으로만 한다.
3. "writer 를 민수킹으로" 는 몇 번 해도 결과가 "민수킹" 으로 같다. "1 더하기" 는 할 때마다 값이 커지므로 두 번 받으면 결과가 달라진다.
4. post-service 그룹이 아직 읽지 않은 소식이 3개 쌓여 있다는 뜻이다. (post-service 가 꺼져 있거나 처리가 밀리고 있다)

## 5장

1. 화면의 닉네임은 바뀌지만, 저장된 토큰은 옛 닉네임 그대로다. 그 뒤에 쓰는 글이 옛 닉네임으로 저장된다.
2. 알 필요 없다. React 는 게이트웨이(8080)에 요청할 뿐이고, 소식을 주고받는 일은 서버 안쪽(user-service, post-service, Kafka)에서 일어난다.

## 6장

1. Kafka 가 post-service 그룹의 읽은 위치를 기억하고 있어서, 다시 켜진 post-service 가 그 다음 소식부터 읽어 가기 때문이다. 다 읽으면 읽은 위치와 쌓인 개수가 같아져 `LAG` 이 0 이 된다.
2. 게이트웨이는 토큰 안의 닉네임을 `X-User-Nickname` 으로 넘기는데, 옛 토큰 안에는 옛 닉네임이 들어 있기 때문이다.
3. 그 소식은 Kafka 에 도착한 적이 없기 때문이다. user-service 가 보내는 순간 Kafka 에 닿지 못해 포기했고, 다시 보내지 않는다.
4. ②는 **받는 쪽**이 꺼졌고 소식은 Kafka 에 남아 있었지만, ④는 **Kafka 자체**가 꺼져 소식이 처음부터 저장되지 못했다.

## 7장

1. `users` 와 `outbox` 가 **같은 DB(userdb)** 에 있기 때문이다. 한 DB 안의 두 테이블은 하나의 트랜잭션으로 묶을 수 있다.
2. 일꾼이 Kafka 로 보낸 뒤 "보냄" 표시를 하기 전에 죽으면 같은 소식을 다시 보내기 때문이다. 받는 쪽이 두 번 받아도 괜찮아야 한다.
3. 소식에 `type` 칸이 있어서, 같은 토픽(`user-events`)에 다른 종류의 소식을 함께 보내고 받는 쪽에서 `type` 으로 나눠 처리할 수 있기 때문이다.
4. JWT 는 서버에 저장하지 않으므로 서버가 취소할 수 없다. 로그아웃한 토큰을 만료 시각까지 어딘가에 적어 두고 요청마다 확인해야 하는데, 요청마다 읽어야 하므로 아주 빠른 메모리 저장소(Redis)가 알맞다. 게이트웨이가 여러 대여도 같은 목록을 함께 볼 수 있다.
